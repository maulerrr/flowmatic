\section{Research Questions}
\label{sec:research_questions}

The evaluation programme in Chapter~\ref{chap:results} addresses the following research questions:
\begin{description}
  \item[RQ1:] Does the Flowmatic preparation workflow deliver measurable quality outcomes (completeness, consistency, latency) on urban traffic uploads before downstream inference?
  \item[RQ2:] Can the preparation workflow be operationalised as a reproducible service with measured end-to-end latency and quality reporting?
  \item[RQ3:] How do the eight production neural models perform across forecasting, reconstruction, imputation, and classification under a common temporal hold-out protocol?
  \item[RQ4:] Does a registry-based Manual/Auto routing policy allow modality-appropriate model selection in a smart-city pipeline?
\end{description}

\section{Evaluation Scope and Validity}
\label{sec:evaluation_scope}

Two validation layers must not be conflated. \emph{Batch platform validation} is demonstrated on the Astana CSV export through the Nest ingestion API (latency, quality score, cleaning). \emph{Neural training validation} uses Astana plus Hugging Face weather, ETT, and traffic-graph bundles prepared offline; those bundles are not all re-uploaded through the Nest API in this thesis. METR-LA and PEMS datasets are excluded from the evaluated dataset table because hold-out experiments were not completed for them in this study.

Experiments use semi-synthetic Astana data with rule-based severity labels. The smart-city demo uses simulated feeds rather than a production agency deployment. External municipal incident-label AUROC, expert-labelled routing accuracy, and live agency deployment remain future work; detailed limitations are discussed in Chapter~\ref{chap:conclusion}.

\section{Data Quality Assessment}

Flowmatic computes a weighted Data Quality Index (DQI) for each upload and pipeline run:
\begin{equation}
\label{eq:dqi}
\mathrm{DQI} = \frac{\sum_{i=1}^{6} w_i Q_i}{\sum_{i=1}^{6} w_i}, \quad Q_i \in [0,1],
\end{equation}
over completeness, consistency, accuracy, timeliness, uniqueness, and validity. Completeness follows $C = 1 - |M|/|D|$; timeliness uses exponential decay $T = \exp(-\lambda \bar{a})$. Table~\ref{tab:dqi_weights} lists default weights $w_i = 1/6$. The NestJS \texttt{QualityService} implements these dimensions via schema typing, duplicate detection, valid-range checks, and Z-score outlier flags.

\section{Preparation and Feature Windows}

After quality assessment, workers apply imputation for missing numeric fields, duplicate removal, and type coercion. For neural training and inference, each sensor stream is windowed into tensors $\mathbf{X} \in \mathbb{R}^{L \times d}$ with $L=48$ by default. Cyclical time encodings
\begin{equation}
f_{\sin}(t) = \sin(2\pi t/P), \quad f_{\cos}(t) = \cos(2\pi t/P)
\end{equation}
and traffic-derived channels (density, speed, severity labels) are materialised in Phase~2 dataset bundles (\texttt{run\_phase2\_prep.py}). Graph models additionally receive adjacency $\mathbf{A}$ for STGCN.

\section{Adaptive Core Unit and Model Registry}

\subsection{Registry}

Each production checkpoint $m$ exposes metadata: kind (e.g.\ \texttt{tranad\_anomaly}, \texttt{transformer\_classifier}), dataset affinity, tasks, sensor kinds, optional geo requirement, and priority. The registry loads from local \texttt{metadata.json} and the Hugging Face manifest (Table~\ref{tab:production-portfolio}).

\subsection{Routing policy}

For sensor kind $k$ and payload features $\mathbf{f}$, the router builds an event profile (modality, preferred task, geo flag). In \textbf{Manual} mode the operator selects model $m^{*}$. In \textbf{Auto} mode:
\begin{equation}
m^{*} = \arg\min_{m \in \mathcal{M}_k} \pi(m \mid \mathbf{f}),
\end{equation}
where $\mathcal{M}_k$ filters incompatible modalities/tasks and $\pi$ is a priority score (lower is better). Anomaly-capable tasks receive precedence when anomaly detection is enabled.

\begin{algorithm}[H]
\caption{Rule-based model routing (Auto mode)}
\begin{algorithmic}[1]
\State \textbf{Input:} sensor kind $k$, payload $\mathbf{f}$, registry $\mathcal{M}$, anomaly flag $a$
\State $\mathit{profile} \gets \textsc{Classify}(k, \mathbf{f})$
\If{$a$ \textbf{and} $\exists m \in \mathcal{M}$ with task anomaly matching $\mathit{profile}$}
  \State \Return best-priority anomaly model (TranAD slot)
\EndIf
\State $\mathcal{C} \gets \{ m \in \mathcal{M} : \mathit{modality}(m)=\mathit{profile.modality} \land \mathit{task}(m)\supseteq \mathit{profile.task}\}$
\State \Return $\arg\min_{m\in\mathcal{C}} \mathit{priority}(m)$
\end{algorithmic}
\end{algorithm}

\section{Neural Evaluation Methodology}

All eight checkpoints share temporal splitting (Table~\ref{tab:split_protocol} in Chapter~\ref{chap:results}), z-score standardisation fit on training windows only, and seed-controlled training (\texttt{phase3\_multiseed\_suite.yaml}). Objectives are defined in Section~\ref{sec:neural_formulations}. Reported metrics use only the held-out 15\% test partition; multi-seed aggregation is $\bar{m} \pm 1.96\,s/\sqrt{n}$ with $n=3$.

\section{Insight Engine and Copilot}

The Insight Engine composes deterministic analytics (hotspots, drift, correlation) with optional LLM narration constrained to retrieved pipeline context. Neural models provide primary diagnostics: reconstruction residuals (TranAD, Equation~\ref{eq:tranad_score}), imputation masks (SAITS), and classification logits (Transformer severity).
